# プロジェクトパートナー

管理者がプロジェクトに割り当てた既存のAI接続を使う3スキル。AIは候補を提案し、タスクへの反映は利用者の明示的な承認で行う。

| 操作 | 場所 | 参照する情報 |
| --- | --- | --- |
| アクション抽出 | 知識 → ノート → AIアシスト | 選択した保存済みノート |
| プロジェクト状況確認 | プロジェクト概要 → 状況を確認 | タスク、依存関係、ノート、過去7日間のタスクコメント |
| 週次報告 | プロジェクト概要 → 週次報告を作成 | 同上。実行時点から過去7日間を明示 |

アクション候補は内容を修正・確認してタスクに追加できる。状況確認・週次報告は生成成功時に自動保存し、概要ページの報告フィードに新しい順で表示する。従来のノート要約と文章改善、別ノート保存は継続する。

## 参照と権限

- `POST /api/projects/[id]/partner` はログインユーザーのプロジェクト編集権限を確認する。閲覧者・コメント専用メンバー・無関係なユーザーには提供しない。
- `readPartnerSnapshot` が一貫した読み取り専用トランザクションで取得する。削除済み情報、他プロジェクトの非共有タスク、参照できない依存先は除外。マルチホームの可視範囲は既存のプロジェクト表示と共通。
- 外部画像・リンク先は取得しない。モデルと接続先は管理者指定。既存の暗号化・接続先制限・同時実行数・利用回数制限を共有する。
- 外部送信直前と結果返却前に権限、設定、参照情報を再確認し、変更された結果は破棄する。
- 全可視タスクの数値をDBで計算する。期限超過は日本時間の日付、期間内完了は `completed_at` で判定。今後7日間は日本時間の当日から6日後まで。
- 詳細はタスク100件、ノート12件、直近コメント20件、依存関係200件を上限とし、管理者の入力文字数上限も適用する。長文は短縮し、件数と部分参照を画面に明示する。集計は全可視タスク、文章による評価は実際に送信した情報のみが対象。

## 提案の扱い

- JSON構造、参照ID、件数・長さをサーバーで検証する。アクションの引用が原文にない場合は表示しない。引用で裏付けられない担当者・期限は「要確認」とする。
- 出典リンクはAtlas側が組み立て、生成テキストはHTMLとして実行しない。
- 参照IDの存在確認は、AIの判断がすべて正しいことを保証するものではない。利用者が根拠を確認できる表示とする。
- `llm_runs` に実行種別・状態・使用量を記録する。生成完了と報告・候補の保存は同じトランザクションで確定する。生成失敗や途中キャンセルでは不完全な報告を残さない。

## アクションの承認

- 候補を1件または複数選び、タスク名・担当者・具体的な期限・追加先セクションを確認する。プレビューの「承認して○件を追加」を押した時点で確定する。
- 敬称・空白の違いを吸収し、氏名または一意に特定できる日本語の姓から担当者を入力済みにする。同姓の候補が複数なら選択を残す。現在のプロジェクトメンバー以外は入力しない。
- 「月曜日」は抽出日（日本時間）から当日を含む次の月曜日、「来週」は月曜始まりの翌週として日付を提案する。「今週」の日付は過去でも翌週へずらさない。今日・明日・明後日・N日後、日本語の年月日にも対応。年のない月日は次に来る日付を提案する。基準日と解釈を表示し、曖昧な指定は空欄にする。再表示でも基準日を変えない。
- アクション抽出には、選択ノートに加えて同一プロジェクトの既存セクション名・IDを入力上限内で最大100件渡す。AIの追加先・理由を提案として保存し、入力に含まれないIDは採用しない。ノートに「○○のセクション」と既存の追加先が一意に明記されていれば、AIの分類よりその指定を優先する。旧候補や提案なしの場合は、候補中のセクション名の一致、または一意の「未着手」「To do」等を補助候補にする。適切なものがなければセクションなしのままにする。利用者が修正した値を再選択や確認画面から戻る操作で上書きしない。
- `GET/POST /api/projects/[id]/partner/actions`。候補を生成した利用者本人かつ現在のプロジェクト編集権限が必要。担当者は有効なプロジェクトメンバー、セクションは同一プロジェクトに限る。
- 候補の根拠はサーバー側に保管し、ブラウザから任意の根拠・候補を追加させない。承認ではモデルを再実行せず、確認した編集内容をそのまま登録する。
- プロジェクトと権限をロックし、全候補の検証後にタスク・承認記録・作成イベントを一括コミットする。1件でも不正なら全件取り消す。元ノートが更新・削除された場合は再抽出が必要。
- 同じノート版・同じ候補の名前と根拠に対する承認は、通信再試行や同じ候補の再生成でも同じタスクを返す。タスク削除後も承認記録を保持し、再試行で再作成しない。異なる文章で生成された候補の意味上の重複判定は行わない。
- 通常のタスク追加と共通の作成・イベント・通知・自動化処理を使う。タスクには安全なリッチテキストで元ノートへのリンクと根拠を残し、承認者と確定した内容を記録する。再試行で作成イベントや通知処理を重複実行しない。

## 報告の履歴

- 概要ページはB案の「全体像」「報告履歴」で切り替える。初期表示と再読み込み時は全体像。目的・実際のオーナー・プロジェクト期限・タスク進捗・マイルストーン・メンバーを表示し、詳細な進捗とアクティビティは展開して確認する。切り替えで説明の未保存の下書きを失わない。
- 生成操作は上部の「プロジェクトパートナー」メニューにまとめ、実行すると報告履歴と結果パネルを開く。全体像には最新報告への一行のリンクだけを置く。報告履歴の件数は保存済みの総件数であり、未読数ではない。閲覧者は履歴を読めるが、生成・確認済み操作はできない。
- `GET /api/projects/[id]/partner/reports` は最新5件を返し、`before` によるカーソルで過去の履歴を取得する。個別の `GET .../reports/[reportId]` で全文・参照元・確認時点・対象期間を開く。
- 本文は生成時のスナップショットとして保持し、再生成では新しい報告を追加する。報告だけでプロジェクト状態やタスクを変更せず、通知も送信しない。
- プロジェクトの閲覧権限があれば保存済み報告を閲覧できる。編集権限のある利用者が `PATCH .../reports/[reportId]` の `reviewed: true` で「確認済み」にできる。本文は変更せず、最初の確認者と時刻を保持する。
- 新マイグレーション0027は `partner_reports`、`partner_action_batches`、`partner_action_approvals` の追加だけ。既存のノート・タスク・接続設定は変更しない。旧版で本文を保存していなかった報告の遡及復元はできない。

## 検証

`npm test`、`npm run typecheck`、対象ファイルのESLint。
`bash tests/run-e2e.sh knowledge-ai` で新規の隔離DB・模擬LLMを使い、既存AIと新3スキル、権限・変更競合・参照範囲・データ保持・キャンセル・PC/モバイル表示、承認の原子性・重複防止・失効、報告の保存・ページング・確認済み・閲覧権限を検証する。保持サーバー65235にはE2Eを向けない。
