# Asanaルール／オートメーション Atlas実装準備調査

作成日: 2026-11-09

## 1. 結論

Atlasにはすでに「簡易オートメーション」があるが、Asanaのルール／オートメーション相当を目指すには**現行実装の延長では不足**している。

現状は「1トリガー + 1アクション」のプロジェクト内マクロであり、条件・分岐・複数アクション・実行主体・実行履歴・日付トリガー・イベント基盤がない。

Asana同等機能に着手する前に、最低限次の5つを前提基盤として実装する必要がある。

1. **全タスク変更を拾うドメインイベント／アウトボックス**
2. **複数トリガー・条件・分岐・複数アクションを表現できるルール定義スキーマ**
3. **非同期ワーカーによるルール実行基盤（再試行・冪等性・ループ防止・履歴）**
4. **ルール所有者と実行権限（run-as owner）**
5. **期日超過・期日接近を実行するスケジューラー**

この5つなしにUIだけAsana風にすると、後で実行基盤を作り直すことになる。

## 2. Asanaルールの仕様（ヘルプセンター調査）

参考:
- https://help.asana.com/s/article/rules?language=ja
- https://help.asana.com/s/article/rule-triggers?language=ja
- https://help.asana.com/s/article/rule-actions?language=ja
- https://help.asana.com/s/article/conditions-and-branching-in-rules?language=ja
- https://help.asana.com/s/article/rule-permissions?language=ja
- https://help.asana.com/s/article/automation-scope?language=ja

### 2-1. 基本構造

Asanaのルールは次の要素で構成される。

- トリガー: ルールを開始するイベント
- 条件: 実行するかどうかの判定
- パス／ブランチ: 条件ごとの実行分岐、elseパス
- アクション: 自動実行する処理
- スコープ: 監視対象と実行対象（このプロジェクト / プロジェクト内容 / 別プロジェクト / ポートフォリオ）
- 実行履歴: いつ、どのタスクで、何が実行されたか

### 2-2. Asanaの主なトリガー例

- タスクが完了したとき
- 期日が設定されたとき／変更されたとき
- タスクがプロジェクトに追加されたとき
- タスクがセクションに移動したとき
- 担当者が変更されたとき
- カスタムフィールドが変更されたとき
- コメントが追加されたとき
- フォームが送信されたとき
- 期日が接近したとき／期限超過したとき
- 手動トリガー
- 外部アプリ／Webhook

### 2-3. Asanaの主なアクション例

- 担当者を変更
- 期日を設定・変更
- セクション／列に移動
- タスクを完了
- コメントを追加
- タスク／サブタスクを作成
- カスタムフィールドを設定
- プロジェクトに追加
- コラボレーターを追加
- プロジェクトのステータスを更新
- 外部アプリへの通知／Webhook

### 2-4. 実行モデル上の重要仕様

- 1つのカスタムルールに最大20トリガー、最大20アクション
- 同一アクションは1回のみ
- プロジェクトあたり最大50ルール
- 条件はAND、パス／ブランチで分岐、elseパスあり
- トリガーとアクションのスコープを個別に指定できる
- プロジェクト内容に対するアクションは、フィルターで対象タスクを絞れる
- 150件を超えるタスクが対象になる実行は拒否される
- ルールは**オーナーの権限**で実行される
- ルールの有効化／無効化・編集はプロジェクトのワークフロー編集権限に依存
- オーナー不在時のオーナーシップ移譲がある
- 実行履歴で、トリガー元タスク・実行アクションを確認できる
- サブタスクは第一階層のみ実行対象（設定による）
- 日付トリガーは「その瞬間」に発火し、既存の期限超過タスクへ遡及しない
- ルールの構成が壊れた場合、オーナーへ通知される

### 2-5. スコープの種類

Asanaはトリガーとアクションで、次の組み合わせを扱う。

- タスク → タスク
- タスク → プロジェクト
- プロジェクト → タスク
- プロジェクト → プロジェクト
- ポートフォリオ → プロジェクト など

Atlasで最初からフル対応するのは過剰。まずは**プロジェクト内のタスク → タスク**に絞るのが現実的。

## 3. Atlasの現状

### 3-1. 既存の簡易オートメーション

実装済み:
- `project_automations` テーブル
- `automation_runs` テーブル
- `/api/projects/[id]/automations`
- `/api/projects/[id]/automations/[automationId]`
- `lib/automations.ts`（トリガー・アクション定義）
- `lib/automation-runner.ts`
- プロジェクト「カスタマイズ」内の自動化パネル
- ルール作成モーダル、有効化／無効化、削除
- ローカル文字列判定の「AIアシスト」
- E2Eの基本オートメーションテスト

現状のトリガー:
- `task_created`
- `task_completed`
- `status_changed`

現状のアクション:
- `set_status`
- `set_assignee`
- `add_comment`

現状の制約:
- 1ルール = 1トリガー + 1アクション
- 条件・分岐・複数アクションなし
- アクション値は単一の `action_value TEXT`
- ルール所有者の概念なし（`created_by` はあるが実行に未使用）
- ルールのバージョン・スナップショットなし
- 実行履歴は成功記録のみ（失敗理由・実行時間・対象アクション列なし）
- ルール削除時に実行履歴もCASCADE削除
- プロジェクトあたりのルール数上限なし

### 3-2. トリガーの発火箇所

現状 `runAutomations()` が呼ばれるのは以下だけ。

| トリガー | 呼び出し元 | 備考 |
|---|---|---|
| task_created | `POST /api/tasks` | 通常のタスク作成のみ |
| task_completed | `PATCH /api/tasks/[id]`、`POST /api/tasks/bulk` | 一括完了も対応 |
| status_changed | `PATCH /api/tasks/[id]` | 一括変更は未対応 |

発火しない経路:
- フォーム送信によるタスク作成
- タスクテンプレートからのタスク作成
- プロジェクトテンプレートからのタスク作成
- 繰り返しタスクの次回生成
- CSV／ファイルインポート
- サブタスク作成の一部経路
- マルチホーム（プロジェクト追加）
- コメント追加
- カスタムフィールド変更
- セクション移動（一括移動含む）
- 担当者変更（一括担当変更含む）
- 期日変更
- プロジェクトステータス更新
- フォーム送信
- 期日接近／期限超過
- 手動実行

### 3-3. アクション実行の現状

`lib/automation-runner.ts` は直接SQLで更新している。

- `set_status`: tasks.statusを直接更新
- `set_assignee`: tasks.assignee_idを直接更新
- `add_comment`: commentsを直接INSERT（author_idはNULL）

このため、通常のユーザー操作が通る以下の処理を通らない。

- タスク更新のバリデーション
- プロジェクト権限チェック
- フィールド編集権限チェック
- task_events（アクティビティ）への記録
- audit_log
- notifyProject／notifyTask（リアルタイム更新）
- ルールの連鎖実行
- 失敗時のロールバック／再試行

さらに `runAutomations()` の呼び出し側は `.catch(() => undefined)` でエラーを握りつぶしているため、失敗がユーザーにも運用にも見えない。

### 3-4. 実行履歴

`automation_runs` は以下だけを持つ。

- automation_id
- task_id
- trigger
- action_type
- created_at

不足:
- 実行ステータス（成功／失敗／スキップ）
- エラーメッセージ
- 実行時間
- トリガーイベントID
- 実行したアクションの一覧と結果
- 実行時点のルール定義スナップショット
- 再試行回数
- 実行主体（owner）
- ルール削除後も残る監査用履歴

### 3-5. 権限

ルールCRUDは `withProject("edit")` で制御されている。
一方、実行時はプロジェクト権限もフィールド権限も確認せず、直接DB更新している。

Asanaのように「オーナーの権限で実行」するには、少なくとも以下が必要。

- ルールに `owner_id` を持たせる
- 実行時に所有者の現在のプロジェクト権限を確認
- アクション対象プロジェクト・フィールド・ユーザーの権限を確認
- ゲスト／閲覧のみユーザーの扱いを決める
- オーナー不在時の移譲・無効化ルール

### 3-6. 非同期実行基盤

現状:
- RedisはWebSocketのlive invalidationにのみ使用
- ジョブキューなし
- 常駐ワーカーなし
- `server.js` の日次janitorのみ
- 期日トリガー用のスケジューラーなし
- Webhookの再送・署名検証なし

そのため、以下は現状では実行できない。

- 期日接近／期限超過トリガー
- 多数タスクへの一括アクション
- 外部アプリ連携
- 失敗時の自動再試行
- 実行履歴の非同期完了更新

### 3-7. 既存のイベント／監査基盤の再利用可否

| 基盤 | 現状 | ルールイベントとしての利用 |
|---|---|---|
| `task_events` | タスクの活動ログ（summary中心） | △ 変更前後・payload・プロジェクトIDがなく、全変更を網羅していない |
| `audit_log` | 操作監査 | △ セキュリティ監査用。ルール実行のドメインイベントには不足 |
| `notifyProject` / Redis pub-sub | 画面更新の通知 | × 永続化されない。キューではない |
| `automation_runs` | 成功記録 | △ 失敗・アクション列・イベントIDがなく実行履歴として不足 |

新しい**ドメインイベント＋アウトボックス**を設けるのが妥当。既存の `task_events` はUIの活動フィード用として残す。

## 4. ギャップ分析

| 領域 | Asana | Atlas現状 | ギャップ | 優先度 |
|---|---|---|---|---|
| ルール構造 | 複数トリガー・条件・分岐・複数アクション | 1トリガー・1アクション | 表現モデルがない | P0 |
| イベント基盤 | 全変更をトリガー可能 | 3トリガーのみ、経路も限定的 | 全変更を拾えない | P0 |
| 実行基盤 | 非同期・再試行・履歴・オーナー権限 | 同期・直接SQL・失敗握りつぶし | 信頼性と権限がない | P0 |
| 条件 | AND条件・パス・else | なし | 条件評価器がない | P0 |
| 実行履歴 | トリガー元・アクション・失敗を表示 | 成功記録のみ | 運用できない | P0 |
| 日付トリガー | 期限接近・超過 | なし | スケジューラーがない | P0 |
| 日付アクション | 期日設定・相対日付 | なし | 日付計算サービスがない | P1 |
| アクション | 作成・移動・フィールド・コメント・追加など | 3種類のみ | アクションサービスが不足 | P1 |
| スコープ | プロジェクト／ポートフォリオ／横断 | プロジェクト内のみ | ポートフォリオモデルがない | P1/P2 |
| 変数 | タスク名・期日などをアクションで利用 | なし | テンプレート展開がない | P2 |
| ルール上限 | 50/プロジェクト、20トリガー/アクション、150件 | 上限なし | 暴走防止がない | P1 |
| テンプレート連携 | プロジェクトテンプレートにルールを含められる | テンプレートpayloadにルールなし | ルール保存形式の確定後に対応 | P2 |
| 複製連携 | プロジェクト複製でルールも複製 | 複製されない | 複製処理の拡張が必要 | P2 |
| バンドル連携 | バンドルにルールを含められる | バンドルはフィールドのみ | バンドル拡張が必要 | P2 |
| 手動実行 | 手動トリガー | なし | 実行APIとUIが必要 | P2 |
| 外部連携 | Webhook、Slack、Gmailなど | なし | 認証・署名・再送基盤が必要 | P3 |
| ルールギャラリー | 構築済みルール集 | ローカルAI提案のみ | レシピ集と適用UIが必要 | P3 |

## 5. 前提として実装すべき機能

### P0: ルールエンジン着手前の必須基盤

1. **ドメインイベント／アウトボックス**
   - `task.created`, `task.completed`, `task.updated`, `task.moved`, `task.assigned`,
     `task.due_changed`, `task.custom_field_changed`, `comment.created`,
     `form.submitted`, `project.status_changed`, `task.added_to_project` など
   - 変更前／変更後、actor、project_id、task_id、workspace_id、発生時刻、一意キー
   - タスク更新と同じトランザクションで記録
   - 既存の `task_events` とは分離

2. **ルール定義スキーマ v2**
   - `triggers[]`（最大20）
   - `conditions`（AND、条件ツリー）
   - `paths[]` / `branches[]`（条件分岐、else）
   - `actions[]`（最大20、同一アクション重複禁止）
   - `owner_id`, `enabled`, `version`, `project_id`
   - ルール数上限、アクション数上限
   - 既存の3トリガー／3アクションからの移行

3. **実行ワーカー／ジョブ基盤**
   - イベント受信→ルール照合→条件評価→アクション実行
   - アウトボックスをポーリングする常駐ワーカー、またはRedisキュー
   - ルール単位・イベント単位の冪等キー
   - 再試行、指数バックオフ、デッドレター
   - 1イベントあたりの連鎖回数制限、同一ルールの再帰防止
   - アクション成功／失敗の履歴

4. **所有者と実行権限**
   - ルール所有者の現在の権限で実行
   - アクション対象プロジェクト・フィールド・担当者の権限チェック
   - 権限喪失時の無効化・オーナー移譲・通知
   - ゲスト／閲覧ユーザーの制限

5. **日付スケジューラー**
   - 期日接近・期限超過の検知
   - 一度だけ発火するための `dedupe key`
   - JST基準の日付境界と実行時刻
   - 既存タスクへの遡及なし

### P1: MVPに必要

6. **全変更経路のイベント発火**
   - 通常のタスク作成・更新
   - 一括操作
   - フォーム送信
   - タスクテンプレート／プロジェクトテンプレート
   - 繰り返しタスク生成
   - インポート
   - マルチホーム追加
   - コメント
   - カスタムフィールド
   - セクション移動
   - 担当者・期日変更
   - プロジェクトステータス更新

7. **共通アクションサービス**
   - タスク更新サービス
   - コメント作成サービス（メンション・通知含む）
   - タスク／サブタスク作成サービス
   - セクション移動サービス
   - カスタムフィールド設定サービス
   - 日付計算サービス（期日+N日、営業日など）
   - すべて監査・イベント・通知・権限チェックを通す

8. **ルールビルダーUI**
   - トリガー選択
   - 条件追加（AND）
   - アクション追加（複数）
   - プレビュー／テスト実行
   - 実行履歴
   - 無効化・エラー状態表示

9. **上限・安全装置**
   - 50ルール/プロジェクト
   - 20トリガー、20アクション
   - 150件超の一括対象を拒否
   - 条件不一致時のスキップ記録
   - 連鎖実行の深さ制限

### P2: Asanaに近づける拡張

- パス／ブランチ／else
- 変数展開（タスク名、期日、担当者など）
- クロスプロジェクトのトリガー／アクション
- 手動トリガー
- プロジェクトテンプレートへのルール同梱
- プロジェクト複製時のルール複製
- バンドルへのルール同梱
- ルールギャラリー（推奨レシピ）
- 構成不備の通知

### P3: フルAsana相当

- ポートフォリオの第一級モデルとポートフォリオルール
- Webhook／外部アプリトリガー
- 外部アクション（Slack、メール等）
- AIによるルール生成
- 大規模テナント向けのキュー水平分散

## 6. 現時点の障害・注意点

### ポートフォリオルールは前提不足

Atlasの「ポートフォリオ」は `portfolio_projects` によるユーザー別の保存リストであり、Asanaのような first-class なポートフォリオエンティティではない。
ポートフォリオ単位のルールを作るには、先にポートフォリオモデル（名前、所有者、メンバー、権限、プロジェクト所属）が必要。

### クロスプロジェクトは可能だが要設計

プロジェクト間アクションは、対象プロジェクトの権限チェックとイベントスコープ設計が必要。
MVPではプロジェクト内に限定し、クロスプロジェクトはP2に落とすのが安全。

### テンプレート／複製との整合

現状のプロジェクトテンプレートpayloadはセクション・タスク・カスタムフィールドのみ。
ルール定義を確定した後、テンプレートpayloadにルールを含める拡張が必要。
同様にプロジェクト複製はルールを複製しない。

### 既存の簡易ルールは移行対象

既存の `project_automations` は1トリガー／1アクションのレガシー形式として残し、
新 `project_rules` へ移行するか、`definition JSONB` を追加して互換変換する。
E2Eの既存自動化テストも新APIに合わせて更新が必要。

## 7. 推奨実装順序

### Phase 0: 基盤（UI変更なし）
- ドメインイベント＋アウトボックス（バージョン付き契約）
- **共通ケイパビリティ／コマンドゲートウェイ**
- **automationモジュールの境界確定（ドメインから automation を直接呼ばない）**
- ワーカー（可能ならアプリプロセス外）
- ルール定義スキーマ v2
- 実行履歴 v2
- 権限／所有者（実行コンテキスト経由）
- 既存ルールの移行

### Phase 1: プロジェクト内MVP
- トリガー: 作成、完了、担当者変更、期日変更、セクション変更、カスタムフィールド変更、コメント、フォーム送信
- 条件: 担当者、セクション、完了状態、ステータス、カスタムフィールド
- アクション: 担当者、期日、セクション移動、完了、コメント、サブタスク作成、カスタムフィールド設定
- 複数アクション
- 実行履歴UI
- 上限・無効化・エラー通知

### Phase 2: Asanaらしい拡張
- 条件分岐／else
- 期日接近・期限超過トリガー
- 変数展開
- クロスプロジェクト
- テンプレート／複製／バンドル連携
- ルールギャラリー

### Phase 3: フル機能
- ポートフォリオルール
- Webhook／外部アプリ
- AIビルダー
- 水平分散ワーカー

## 7.5 疎結合アーキテクチャ評価（AIアシスタント共存の観点）

### 結論

現計画は「イベント駆動」「ワーカー分離」「共通アクションサービス」に触れており方向性は正しい。
ただし、**このままでは不十分**で、次の密結合が残る。

| 現計画／現コード | 問題 | あるべき姿 |
|---|---|---|
| APIルートが `runAutomations()` を直接呼ぶ | ドメイン → automation の逆依存 | ドメインはイベントを記録するだけ。automationは購読側 |
| ランナーが tasks/comments を直接SQL更新 | ドメイン内部・権限・監査・イベントを迂回 | 共通ケイパビリティ（コマンド）経由 |
| UIがトリガー／アクションenumを直接import | エンジン変更がUIに波及 | バックエンドのディスクリプタAPIで駆動 |
| ルール定義が task/project の列名に直結 | AIや他ドメインが再利用できない | 汎用イベント＋ケイパビリティID＋パラメータ |
| 権限チェックをAtlasの認証関数に直結 | automation/AIごとに権限実装が重複 | 実行コンテキストの権限アダプター |
| ワーカーをNext.jsアプリ内で実行 | デプロイ・スケール・AIジョブと干渉 | 独立ワーカー／ジョブ実行基盤 |
| 実行履歴が task_id 前提 | プロジェクト・コメント・AI実行を表現できない | 汎用 subject / event_id / action結果 |

### 目標とする依存方向

```text
Atlasドメイン
  └─ ドメインイベント／アウトボックス（公開契約）
        ├─ Automationモジュール（購読・ルール照合・条件評価）
        │     └─ ケイパビリティゲートウェイ（公開コマンド）
        └─ AIアシスタント（将来：購読・提案・実行）
              └─ 同じケイパビリティゲートウェイ

Atlasドメイン ─X→ Automation（直接呼び出し禁止）
Automation ──→ Atlasドメインの公開コマンドのみ
AI ─────────→ Automationの公開サービス＋公開コマンドのみ
```

ポイントは、**AutomationとAIを兄弟の消費者として扱う**こと。
AIだけのためにAutomation内部へフックを追加したり、AutomationがAI専用APIを持つ必要はない。

### 追加で必要な公開契約

1. **バージョン付きドメインイベント**
   - `id`, `type`, `version`, `occurred_at`, `workspace_id`, `actor_id`
   - `subject`（task / project / comment など）
   - `data`（変更前後、変更内容）
   - `correlation_id`, `causation_id`
   - 追加フィールドは後方互換。イベント型ごとにスキーマを管理

2. **ケイパビリティ／コマンドゲートウェイ**
   - 例: `task.assign`, `task.set_due_date`, `task.move_section`, `task.complete`,
     `comment.add`, `task.create_subtask`, `field.set_value`, `project.set_status`
   - 各ケイパビリティは `describe` / `authorize` / `execute` を持つ
   - 権限・監査・イベント・通知・バリデーションを共通化
   - AutomationもAIも同じ入口を使う

3. **実行コンテキスト**
   - `actor`（ルール所有者またはAI操作ユーザー）
   - `source`（`automation` / `ai` / `manual`）
   - `permissions`（プロジェクト／フィールド権限アダプター）
   - `correlation_id`

4. **汎用ルール定義**
   - `trigger`: イベント型 + フィルター
   - `conditions`: 条件ツリー
   - `actions`: ケイパビリティID + パラメータ
   - タスクのSQL列名や実装クラスを直接埋め込まない

5. **ディスクリプタAPI**
   - 利用可能トリガー、条件、アクション、パラメータスキーマを返す
   - UIはこの情報からフォームを生成
   - AIアシスタントも同じディスクリプタを読んでルール案を生成できる
   - これにより、トリガー追加時にReact側のenumを変更しなくて済む

### モジュール境界の目安

```text
lib/domain/            … タスク・コメント・プロジェクトの公開コマンドとイベント契約
lib/capabilities/      … ケイパビリティ登録・実行・権限アダプター
lib/automation/        … ルール定義、照合、条件評価、実行、履歴
lib/automation/worker  … アウトボックス購読／ジョブ実行
app/api/automations/   … 薄いHTTPアダプター
components/automation/ … ディスクリプタ駆動のUI
```

- 同一DBでもよい。結合を避けるのは「コードの依存方向」と「テーブル所有権」
- `tasks` などのコアテーブルから automation テーブルをJOINしない
- Automationはコアの公開コマンド／イベント契約にのみ依存する
- AIはAutomationの内部実装ではなく、公開APIとケイパビリティに依存する

### AIアシスタントとの接続

AIアシスタント実装時に、Automation内部を変更せずに済む形にする。

- AIはドメインイベントを読んで状況を理解する
- AIはケイパビリティゲートウェイ経由で操作する
- AIは `AutomationService.validate()` / `create()` でルールを提案・作成する
- AIは実行履歴を読んで「なぜ動いたか」を説明する
- AIの操作も `source: "ai"` の実行コンテキストで監査する

### 過剰抽象化の注意

- 最初から任意のエンティティを扱う汎用ワークフローエンジンにはしない
- まずは task / comment / project の小さなケイパビリティ集合に絞る
- イベント契約とコマンド境界だけを安定させ、内部実装は段階的に育てる
- 疎結合の目的は「何でもプラグイン化」ではなく、**Automation・AI・ドメインの変更理由を分離すること**

---

## 8. 判断

- **現行の簡易オートメーションをそのまま拡張してAsana相当にするのは非推奨。**
- UIより先に、イベント基盤・ルールスキーマ・実行ワーカー・権限・履歴を作るべき。
- まずはプロジェクト内タスクのMVPに絞れば、既存のプロジェクト・タスク・カスタムフィールド・フォーム資産を活用できる。
- ポートフォリオ／クロスプロジェクト／外部連携は、MVPの後に段階的に追加するのが現実的。
- **疎結合の要は、ドメインがAutomationを呼ばないこと、副作用は共通ケイパビリティ経由にすること、UIとAIが公開契約だけに依存すること。** この3点をPhase 0で決めれば、将来のAIアシスタントと共存しやすい。
