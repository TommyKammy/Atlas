# 通知の配信と運用

受信トレイは未読・既読・すべてをSQLで絞り込んでから50件ずつ取得する。日時（マイクロ秒）、ID、種別のカーソル順で次のページを取得できる。各タブの総件数とサイドバーの未読数は同じ閲覧権限・プロジェクト通知設定を使用する。自分の投稿は未読数に含めない。承認通知は指定された受信者だけに表示・配送する。

`notifications.in_app=false` は対象プロジェクト経由の受信トレイと未読数を停止する。`notifications.email=false` は新しいメールソースの作成と待機中メールの配送を停止する。複数プロジェクトに属するタスクは、有効かつ閲覧可能な所属のいずれかが通知を有効にしていれば通知対象になる。古い不整合な親子データから、異なる主プロジェクトの親の権限を継承しない。

## メール設定

カスタムサーバー `node server.js` が独立したメールワーカーを起動する。`next dev` / `next start` だけでは起動しない。`NOTIFICATION_WORKER_DISABLED=1` はワーカーを無効にする（使い捨てAPI回帰環境では必須）。プロジェクト設定の通知タブはSMTP設定の有無、ワーカーの最近のハートビート、配送件数を表示する。接続可能性は送信まで未確認なので「SMTP受付済み」はSMTPが宛先を受理した場合だけ記録し、受信箱への到着を保証する表現はしない。

必要な環境変数は `SMTP_HOST` と信頼済みの `APP_URL`（または `APP_ORIGIN`）。リンクのホストにはHTTP要求のHostを利用しない。必要に応じ `SMTP_PORT`（既定587）、`SMTP_SECURE=1`、`SMTP_USER`、`SMTP_PASS`、`SMTP_FROM` を指定する。465番はTLSを利用する。認証情報はAPIや設定画面に返さない。

前方マイグレーション `0017_notification_delivery.sql` は新規コメント・タスクイベントだけをキューに積む。導入以前の履歴は送信しない。SMTP未設定でもタスク更新は成功し、メールは未接続として保留する。設定追加後に保留メールを自動で一斉送信しない。設定画面で管理者が明示的に再試行する（1回最大100件）。通常のSMTP失敗は5秒・30秒後に再試行し、合計3試行で失敗とする。

ワーカーは1回最大20件を処理する。各配送直前に現在のユーザー有効性、プロジェクト削除、所属・閲覧権限、メール設定、承認宛先を再確認する。対象外になった待機メールは取消となる。プロジェクト削除とのロック順序は既存自動化と共通のトランザクション共有ゲートで揃える。

処理中リースが期限切れになった配送や、SMTP受理後に結果のDB保存に失敗した配送は受理状況不明として失敗にし、自動では再送しない。停止前にSMTPが受理して応答だけ失われた場合、固定Message-IDでも重複配送を完全には防げない。接続切断など受理結果を確認できなかった場合は自動リトライでも重複する可能性があり、管理者による失敗メールの再試行にも同様の可能性がある。送信前に停止したclaimは試行回数を消費しない。

Docker起動は `exec node server.js` でSIGTERM/SIGINTをNodeへ渡す。停止時には新しいメールclaimとHTTP要求（自動化内部要求を含む）を停止し、WebSocketを閉じ、進行中SMTPとHTTPを待ってからDBプールを閉じる。排出は8秒が上限で、超過時は受理状況不明の可能性を記録して終了する。リース切れ処理がその配送を失敗にし、後から明示再試行できる。

## 回帰試験

`tests/ev10-regressions.mjs` は既存の使い捨てDBガードを利用し、すべてのメールにメモリ内トランスポートを注入する。実SMTPや外部配送は行わない。未読100件外の取得、同時刻カーソル、設定正規化、親子・多ホーム・承認宛先、SMTP未設定、排他claim、権限失効、失敗リトライ、送信中リース切れ、プロジェクト削除との共有ゲートを検証する。純粋なカーソル・設定・停止シーケンスはNode単体テストで検証する。
