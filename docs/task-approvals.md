# 承認タスク

## 対象範囲

通常タスクに1名の承認者を指定して申請し、承認・却下・差し戻し・再申請・承認者変更を扱う。
長時間待機するワークフロー、承認後の実行再開、複数承認者の決裁、代理承認は含まない。

タスクの「承認リクエスト」メニューから詳細パネルの承認セクションを開く。
承認状態は一覧・ボードのバッジにも表示する。通常の完了操作は専用の承認操作へ誘導する。

## 状態と権限

| 操作 | 実行者 | 遷移 |
|---|---|---|
| 申請 | 主プロジェクトを編集できるユーザー | 通常タスク → 承認待ち |
| 承認 | 指定承認者 | 承認待ち → 承認済み |
| 却下 | 指定承認者、理由必須 | 承認待ち → 却下 |
| 差し戻し | 指定承認者、理由必須 | 承認待ち → 差し戻し |
| 再申請 | 申請者または主プロジェクト管理者 | 判断済み → 新しい申請回の承認待ち |
| 承認者変更 | 申請者または主プロジェクト管理者 | 承認待ち → 新しい申請回の承認待ち |

- 各操作には現在の主プロジェクトの編集権限が必要。副所属だけの編集権限では申請・判断できない。
- 承認者には主プロジェクトを編集できる有効なユーザーを指定する。閲覧者、所属外で編集権限のないユーザー、無効化ユーザーは指定できない。
- 申請者と承認者は別人。管理者も、指定承認者の代わりに承認・却下・差し戻しを行うことはできない。
- 各申請回の申請・再申請・承認者変更の実行者も、自分を承認者に指定できない。元の申請者を維持して管理者が再申請する場合にも適用する。
- 申請者を維持したまま承認者を変更できる。旧承認者や旧申請回の画面からの判断は受け付けない。
- 承認済みだけがタスクの完了状態になる。他の状態は未完了。完了済みの通常タスクを申請すると未完了に戻る。
- 承認タスクとマイルストーン・繰り返しは併用しない。単独PATCH、一括操作、自動化の通常完了アクションから承認を迂回することも拒否する。
- 却下・差し戻し後は通常のタスク編集で修正し、再申請する。判断にはタスクの更新時刻も必要なため、取得後に内容が更新された画面からは判断できない。
- 承認後も通常のタスク編集は可能で、過去の承認判断を自動的には失効させない。変更内容の再確認が必要な場合は明示的に再申請する。文書や添付ファイルの版を固定する決裁機能は含まない。
- タスクの複製は未完了の通常タスクとして作成し、承認者・決裁結果・判断履歴を引き継がない。プロジェクト複製でも承認タスクの完了状態を引き継がない。

## 保存・競合・履歴

`0016_task_approvals.sql` で次のテーブルを追加する。ベースラインの `db/init.sql` は変更しない。

- `task_approvals`: タスクごとの現在状態、承認者、申請者、申請回、更新バージョン。
- `task_approval_history`: 操作ごとの申請回・バージョン・実行者・承認者・理由・日時。ユーザー名は判断時の名前も保存する。
- `task_event_recipients`: 既存のタスクイベントに対する通知対象。

更新・完了状態・履歴・通知宛先・監査・ドメインイベントは同じトランザクションで保存する。
承認により未完了から完了へ変わる場合、既存の完了イベントを発行し、旧方式の完了時自動化も通常タスクと同じ方針でコミット後に実行する。
プロジェクト削除との共通共有ロックを行ロックより先に取得し、タスク行をロックして権限とバージョンを再検証する。
タスクと承認状態の整合性は遅延制約トリガーでも検査する。通常タスクの日付変更にはこの制約トリガーを発火させない。

二重判断や古いタスク・申請バージョンは409。UIは入力した理由を保持し、明示的に最新情報を読み込んでから操作を再開する。
承認者の無効化や権限喪失後は判断できないため、申請者または主プロジェクト管理者が有効な承認者へ変更する。
共有タスクの主所属が変わった場合も、その時点の主プロジェクトの権限で検証する。

## 通知

申請・再申請は承認者へ、承認・却下・差し戻しは申請者へ通知する。
承認者変更は新旧承認者と申請者のうち、操作実行者以外へ通知する。
通知は既存の受信トレイ・既読操作を使い、現在のタスク閲覧権限も確認する。
タスクを閲覧できるユーザーは詳細の判断履歴を参照できる。

## API

`GET /api/tasks/:id/approval` は現在状態、判断履歴、承認候補、操作権限、現在の `task_updated_at` を返す。

`POST /api/tasks/:id/approval`:

```json
{
  "action": "request",
  "approver_id": 2,
  "comment": "内容の確認をお願いします",
  "expected_version": 0,
  "expected_updated_at": "GETで取得したtask_updated_at"
}
```

`action` は `request` / `approve` / `reject` / `request_changes` / `resubmit` / `reassign`。
初回バージョンは0。それ以降はGETまたは直前の更新応答のバージョンを送る。
承認・却下・差し戻しでは保存済み承認者を使用し、クライアントが送る別の承認者へ判断を付け替えない。

## 検証

専用の使い捨て環境:

```bash
bash tests/p0-regressions.sh approval
```

APIの `all` / `integrity` モードにも含まれる。ブラウザの申請・差し戻し・再申請・承認・競合表示は `tests/browser/task-approval.spec.ts` で検証する。
全体検証は `npm run typecheck`、`npm run lint`、`npm test`、`bash tests/p0-regressions.sh all`、`bash tests/run-e2e.sh shell`、`bash tests/run-e2e.sh browser`。
既存DBや操作用の3,000件環境を回帰テストの接続先にしない。
