# 二要素認証の秘密鍵の保存と移行

TOTPの有効な秘密鍵と登録途中の秘密鍵は、アプリケーション側のAES-256-GCMで暗号化して保存します。暗号文には形式の版、鍵ID、ランダムな96bit nonce、認証タグを含め、ユーザーIDとactive/pendingの用途をAADに結び付けます。他ユーザーや登録途中の列へ暗号文をコピーしても検証できません。リカバリーコードは従来どおりハッシュ保存です。

## サーバーの鍵設定

すべてのアプリ・認証API・マイグレーション実行プロセスに、同じサーバー専用設定を渡します。

```text
MFA_ENCRYPTION_KEY_ID=key-2026-11
MFA_ENCRYPTION_KEYS={"key-2026-11":"<32バイトのランダム鍵を標準Base64にした値>"}
```

上記は置換が必要な例であり、有効な鍵ではありません。鍵は`openssl rand -base64 32`などの暗号学的な乱数生成器で作り、シークレット管理基盤から注入します。`NEXT_PUBLIC_`変数、Git、SQL、監査ログ、クライアント設定へ入れません。DBバックアップだけでは復号できないよう、鍵の保管・復旧経路をDBと分離します。

- 鍵IDは英数字・ハイフン・アンダースコアの1〜32文字。
- キーリングはJSONオブジェクトで最大16鍵。値は厳密な標準Base64の32バイト鍵で、書込用IDが必ず含まれている必要があります。
- 新しい書込は`MFA_ENCRYPTION_KEY_ID`の鍵を使い、既存暗号文の読込はその暗号文に記録されたIDを使います。
- 既定鍵、パスワードからの鍵生成、起動ごとの一時鍵、平文へのフォールバックはありません。
- 鍵不足・形式不正・改ざん・復号不能では認証を成功させず、MFA APIは秘密値を含まない503を返します。リカバリーコードを使う既存の本人確認は、暗号化したTOTP鍵の復号を必要としません。

## 既存の平文データの移行

`0018_mfa_secret_encryption.sql`は、`scripts/migrate.ts`のNode側処理と組み合わせて適用します。SQLファイルだけを直接流して既存値を暗号化する方式ではありません。

1. 対象DBに2FA秘密鍵がある場合、適切な鍵設定を渡してから通常のマイグレーターを実行します。
2. 一つのトランザクションでusersをロックし、有効／登録途中の平文を暗号化します。
3. その後、暗号文の形式以外を拒否するDB制約を追加し、マイグレーション台帳と一緒にコミットします。

鍵が未設定・不正で既存値を変換できなければ、0018全体をロールバックします。台帳だけを適用済みにしたり、片方の列だけを変換済みにしたりしません。既に暗号化されている値も復号できることを確認します。秘密鍵のない空DBは、鍵未設定でもこのマイグレーションとアプリの起動が可能ですが、MFA登録を開始する前に鍵設定が必要です。

ロック中はユーザー情報の読書きが待機するため、実環境への適用は認証処理を排出したメンテナンス時間帯に行います。この変更の検証では既存DBには適用せず、新しい使い捨てDBだけを使います。

移行前に作成されたバックアップや過去のWAL・古い行バージョンを、この移行が遡って暗号化・消去することはありません。既存の保管物のアクセス制御・保持期間も別途管理します。

## 鍵のローテーション

1. 旧鍵と新鍵を含むキーリングを全アプリへ配布し、すべてのプロセスが両方を読める状態にします。
2. 書込用IDを新鍵に切り替えます。旧鍵はまだ削除しません。
3. 認証の書込を排出し、同じキーリングを渡して次を実行します。

```sh
npx tsx scripts/rotate-mfa-secrets.ts --apply
```

このコマンドは明示的な`--apply`がないと実行しません。通常のマイグレーターと同じ排他ロックを取り、認証処理と同じ「ポリシー→ユーザー」の順にロックして、全対象値を一つのトランザクションで再暗号化します。旧鍵が不正・不足している値があればロールバックし、ログには変換件数だけを出します。既に書込用IDの値は検証後に維持するため、同じ設定の再実行で暗号文を無用に書き換えません。ロックを5秒以内に取得できない場合も失敗して戻ります。

全稼働データが新鍵へ変わった後も、旧DBバックアップを復旧するには旧鍵が必要です。バックアップ保持期間と復旧手順を確認したうえで、旧鍵を別管理に退避するか廃棄します。鍵を紛失した場合に暗号文からTOTP秘密鍵を復元する機能はありません。既存の本人確認・管理者リセット手順で再登録します。

## 回帰検証

- 純粋テスト：往復・nonceの非再利用、ユーザー／用途の付替え拒否、暗号文改ざん、平文拒否、鍵の形式とローテーション。
- API：登録途中も保存済みも暗号文、pendingからactiveへの再暗号化、実際のTOTPログイン、改ざん／列・ユーザー付替えの503とセッション未発行。
- 使い捨てDB：鍵なし移行のロールバック、鍵を与えた再試行、両列の変換、冪等性、空DBの起動、平文再書込のDB拒否、鍵更新と誤った旧鍵の全体ロールバック。

テスト用の固定鍵は純粋テスト内だけにあり、アプリの既定値ではありません。実行環境の回帰テスト用鍵は各使い捨て環境で新しく生成します。
