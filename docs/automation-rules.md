# Atlas ルール／オートメーション実装

Asanaのルール／オートメーションを参考に、Phase 0〜3の基盤と機能を実装した。

## アーキテクチャ

```text
Atlasドメイン
  └─ domain_events（イベント／アウトボックス）
        ├─ automation engine / worker
        │     └─ capabilities（共通コマンド）
        └─ 将来のAIアシスタント
              └─ 同じcapabilities／公開API
```

- ドメインはAutomationを直接呼ばない
- Automationはイベントを購読し、副作用は共通ケイパビリティ経由で実行
- UIはディスクリプタAPIでトリガー・条件・アクションを描画
- AIアシスタントは将来、同じイベント・ケイパビリティ・ルールAPIを利用可能

## Phase 0: 基盤

実装済み:
- `domain_events` アウトボックス
  - type/version/subject/data/causation/chain_depth/processing状態
- `project_rules` 汎用ルール定義
  - triggers[], conditions[], actions[], branches[]
  - owner_id / enabled / version
- `rule_runs` 実行履歴
  - status / actions_total / succeeded / failed / error / details
- `automation_fires` 日付トリガーの重複発火防止
- 共通ケイパビリティ `lib/capabilities`
- ワーカー `/api/automation/process`
  - `FOR UPDATE SKIP LOCKED` で複数ワーカー対応
  - instrumentationから2秒ごとに起動
- 所有者の権限で実行
- 既存の簡易 `project_automations` は互換用として残存

## Phase 2: 拡張

## Phase 3: 発展

- Webhookアクション
  - 公開 IP の HTTP(S) 宛先のみ。DNS 検証済みの IP に接続し、リダイレクトは拒否
  - シークレット設定時は受信仕様と同じ v2 署名を送信。外部受信側との互換性のため本文のみの旧 `x-atlas-signature` も送信
  - タイムアウト10秒
- AIルールビルダー
  - `/api/projects/[id]/rules/ai-suggest`
  - ローカル自然言語ヒューリスティック
  - LLMへ差し替え可能なAPI境界
- 水平ワーカー対応
  - `SKIP LOCKED`
  - イベント処理の冪等チェック
  - 連鎖深度制限
- 実行履歴の保持
- 日次janitorでdomain_events / rule_runsを保持期間後に削除

## API

- `GET/POST /api/projects/[id]/rules`
- `PATCH/DELETE /api/projects/[id]/rules/[ruleId]`
- `GET /api/projects/[id]/rules/[ruleId]/runs`
- `POST /api/projects/[id]/rules/[ruleId]/run`
- `GET /api/projects/[id]/automation/descriptors`
- `POST /api/projects/[id]/rules/ai-suggest`
- `POST /api/automation/process`（内部ワーカー用トークン）

## 制限

- ルール上限: 50/プロジェクト
- トリガー: 20/ルール
- アクション: 20/ルール
- 条件: 30/パス
- 日付トリガーの対象: 150タスク/ルール
- 連鎖深度: 8

## 追加実装（Phase 2/3 残項目）

### ポートフォリオルール
- first-class ポートフォリオモデルを追加
  - `portfolios`
  - `portfolio_items`
  - `portfolio_rules`
- ポートフォリオルールは全所属プロジェクトの `project_rules` にレプリカとして射影
  - 既存のルールエンジン・実行履歴・権限・ケイパビリティをそのまま利用
- プロジェクト追加時にレプリカを自動作成
- プロジェクト削除時にレプリカを自動削除
- ルール更新時に全レプリカを同期
- `/portfolio` に共有ポートフォリオ、プロジェクト追加・削除、ポートフォリオルールUIを追加
- ポートフォリオ単位の集約実行履歴

### バンドルのルール同梱
- `bundles.rules` を追加
- バンドル作成時に現在のプロジェクトルールを選択して同梱
- バンドル適用時にルールを対象プロジェクトへ作成
- 適用済みバンドルの再適用では重複作成しない
- バンドル一覧にルール名を表示

### 外部Webhookトリガー
- `automation_webhook_endpoints` を追加
- プロジェクトごとに受信URLと署名シークレットを発行
- `POST /api/automation/webhook/[token]` を追加
  - `x-atlas-timestamp` は Unix 秒。サーバー時刻との差は5分以内
  - `x-atlas-delivery-id` は配信ごとに一意な英数字・`_`・`-` の1〜128文字。同じ配信の再送では同じ ID を使用
  - `x-atlas-signature-v2` は `timestamp.delivery-id.` に未加工の本文バイト列を連結した入力の HMAC-SHA256 を16進数にした値
  - 成功は202、署名不正・期限切れは401、同一エンドポイントへの再送は409、256 KiB 超は413。配信 ID は24時間保持
  - `webhook.received` ドメインイベントを発火
- ルールUIに受信Webhookの作成・URLコピー・削除を追加
- Webhookトリガーから `task.create` などのアクションを実行可能
- 既存の署名なしエンドポイントは無効化されるため、署名用シークレットを設定して作り直す。既存の署名付き URL は維持され、送信元は v2 ヘッダーへの更新が必要
- ルールの実行履歴に URL・署名シークレットを出さない。プロジェクト複製・テンプレート・バンドル適用でコピーされる Webhook ルールは無効になり、新しい所有者が宛先を設定する
- 旧バージョンで閲覧者に表示された受信 URL と送信署名シークレットは、外部の送受信設定と合わせて更新する

### アクション再試行
- 最初の実行時に分岐と展開済みの引数を記録する。DB 内のアクションは変更、監査、イベント、次のアクション位置を同じトランザクションで保存する
- ワーカーは有効なリースの所有者だけが進捗を書き込める。中断後は完了済みのアクションを飛ばし、未完了のアクションから再開する
- 一時的な失敗はバックオフ付きで最大3回まで実行する（`AUTOMATION_ACTION_MAX_ATTEMPTS` で変更可能）。権限や入力のエラーはその場で失敗として記録する
- 外部 Webhook の再試行では同じ本文と `Idempotency-Key`／`x-atlas-delivery-id` を送る。受信側が配信 ID で重複を拒否する場合に、応答を失った再送での二重反映を防げる
- 0007 の適用前に旧ワーカーを停止する。旧ワーカーが一度でも処理を開始した未完了イベントは、既に副作用が発生している可能性があるため失敗として保留する

### プロジェクト削除との排他制御

- イベントの claim、実行・完了・再試行の更新、日付トリガーの cursor／outbox 保存は、行ロックより先に共通の transaction advisory gate を共有モードで取得する。通常のワーカー同士は並行して処理できる
- プロジェクトのゴミ箱移動・完全削除は、タスクの主所属変更や削除より先に同じ gate を排他モードで取得し、トランザクション終了まで保持する。この間は全プロジェクトの automation の DB 更新ステージが待機する。Webhook の外部 I/O は gate の外で実行する
- リース付き実行の既存の `lock_timeout` は5秒。gate 待機がこれを超えると `55P03` でそのトランザクションをロールバックし、既存の再試行・リース回収方針に従う。長い削除中は自動化の実行が遅れる場合がある
- 既存環境へ適用する際は、旧ワーカーを停止し、実行中の処理を排出してから全アプリ replica を同じ更新版へ切り替え、ワーカーを再開する。アプリ内の定期実行・内部 process API・手動実行も対象とし、新旧バージョンを混在稼働させない。旧版は共通 gate に参加しないため、混在中の排他は保証されない
- 回帰は `bash tests/p0-regressions.sh project-delete [1〜500の繰り返し数]` で専用の使い捨て環境に実行する。14グループ、繰り返しごとに16通りの同時実行順序と、実行全体で1回の5秒タイムアウト後の回復を検証する（合計 `16 × 繰り返し数 + 1`）。`integrity`／`all` にも1回ずつ含む。既存 DB や操作用環境には接続しない

### 手動実行と履歴

- 手動実行は有効な `task.manual_rule` トリガーを持つプロジェクトルールだけに許可する。ポートフォリオの複製ルールはプロジェクト API から実行・閲覧できない
- `POST /api/projects/[id]/rules/[ruleId]/run` は作成したイベントだけを処理し、`event_id`、`status`、`error` を返す。状態は `success`、`failed`、`skipped`、`queued`。実行待ちは202、終端状態はイベント作成の201を返す
- 実行待ちは同じルールの `runs?event_id=...` で確認する。画面を閉じても開始済みの処理は取り消されない。削除やアクセス権の変更で結果を取得できない場合は確認を停止し、成功とは表示しない
- 履歴を閉じる・切り替えると以前のリクエストを中断する。取得中、取得失敗、履歴なしを区別して表示する

### 日付トリガーと入力検証

- `days` 省略時は期日接近を1日前、期限超過を0日として保存・実行する。明示された0日は保持する
- `0013_due_soon_scan_cursor.sql` は期日接近のスキャン開始日を保持する。初回はその日のJST日付から開始し、150件のバッチ上限や日付変更、再起動、outbox保存失敗の後も未処理分を取得する。fire keyとイベントは同じSQLで保存する
- 条件・アクション・分岐の不正な型や不明な条件フィールドを保存時に拒否する。カスタム条件は対象プロジェクト内のフィールドと値の型も検証する。新規ルールの `enabled: false` はプロジェクト・ポートフォリオと複製先で維持する
- 共有タスクのセクション移動はイベントの操作元プロジェクトに適用する。副所属の移動はそのmembershipとタイムラインpinだけを変更し、主プロジェクトの配置を保持する。実変更時は既存の競合検出に使う `tasks.updated_at` も更新する

### 専用ワークフローエディター

- カスタマイズの「フローを作成」「フロー編集」から、`/projects/[id]/rules/new` または `/projects/[id]/rules/[ruleId]` を開く。既存の簡易フォームと API は維持する
- Atlas の共通ヘッダー・左ナビ・配色を使い、中央にカード式フロー、右側に選択したステップの設定を表示する。小さい画面では設定パネルを閉じてフローへ戻れる
- 担当者・タスク・セクション・参照先は名前で検索する。条件の型に合う比較方法と値を使い、変数は挿入メニューから選ぶ。アクションと分岐は上下移動・複製・削除・Undo/Redoに対応する
- 既存 v1 の意味を維持する。きっかけは OR、共通条件・各パスの条件は AND、通常パスは上から最初の一致だけを実行し、「それ以外」は最後に評価する
- 編集・公開は所有者が行う。他の閲覧可能なメンバーは公開版だけを閲覧でき、所有者の下書きとWebhookの宛先・キーは取得できない

### 下書きと公開版

- `0014_project_rule_drafts.sql` の `project_rule_drafts` に下書きを保存する。カードが未完成でも保存でき、公開中のルール定義・バージョンは変わらない
- 約1.2秒の自動保存、明示保存、再読込、下書き一覧からの再開に対応する。新規下書きのURLは `new?draft=UUID`。一覧は自分の未公開・変更ありの概要だけを最新50件まで表示する
- 保存は `expected_revision`、公開は下書き revision と公開版の version/updated_at を検証する。競合時は入力を保持し、明示的に最新状態を読み込む。破棄した保存キューは再開しない
- 設定画面の「下書きを破棄」は公開版を保持して下書きだけを削除する。終了時の自動保存で破棄した下書きを再作成しない
- 公開は同じ revision での再送を二重作成にしない。公開ボタンを押したスナップショットを反映し、停止状態での公開も可能。Webhook の参照IDはサーバーの応答と同期する
- 内部リンクへの移動前とSPAのページ終了時に未保存分の保存を試みる。ページ全体の再読込・終了で未保存の場合はブラウザの離脱確認を使う

### 条件の未入力チェック

- 比較値が必要な条件は、未入力・空白のみ・`null`・空配列・空の候補を含む配列のまま公開できない。共通条件とすべてのパスを検証し、APIからの直接作成・更新・再有効化でも同じ制約を適用する
- 空かどうかの判定には「空である」「空でない」を選ぶ。この2つの比較方法に値は不要。数値の `0`、真偽値の `false`、条件がないフローは有効な設定として扱う
- エディターは未入力の条件を一覧と入力欄の両方で示す。一覧から該当する条件の設定へ移動でき、修正すると公開可能になる。未完成の内容は下書きへ保存・再開でき、公開済みルールには反映されない
- 既存の公開済みルールを自動的に書き換えたり、実行時の条件評価を変更したりはしない。古い空値比較を編集・再公開する際は、意図に合う比較値または明示的な空判定へ変更する

### テストと評価履歴

- 「テスト」で想定イベントと対象タスクを選び、現在の下書きを変更せずに評価する。任意のイベントデータは詳細設定で指定できる
- プレビューと実行は `evaluation.ts` の評価器を共有する。プレビューは読み取り専用トランザクションでスナップショットを読み、タスク・履歴・outboxを変更せず、DNS照会やWebhook送信もしない
- プレビューは条件の現在値と判定、選択されたパス、展開後のアクション、実実行との差に関する注意を表示する。実行時の権限・制約・外部通信の成功を保証するものではない
- `0015_rule_evaluation_history.sql` により、以後の実行履歴へ条件・分岐の判定理由を記録する。履歴には比較値・実データ・Webhook秘密情報を保存しない。旧履歴とスキップの記録方針は維持する
- 待機・承認後の再開、条件内のORや入れ子、並列処理は今回の範囲に含まない
